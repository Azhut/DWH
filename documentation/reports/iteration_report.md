# Отчёт о проделанной работе (текущая итерация проекта)

## 1. Введение

Проект представляет собой серверное веб-приложение для приёма, обработки и предоставления данных статистической отчётности (Excel-файлы) Министерства спорта Свердловской области. Ключевая задача системы — преобразование входных отчётных документов в нормализованное хранилище (MongoDB) с возможностью последующей выборки данных через API.

Текущий этап работ является **следующей итерацией** после архитектуры, описанной в предыдущем отчёте как **«новая архитектура системы»** (многослойность, сущность `Form`, единый конвейер обработки, `Unit of Work`, внедрение зависимостей). В настоящем документе описаны изменения и развитие системы относительно этого состояния.

## 2. Базовое состояние (предыдущая итерация: «новая архитектура системы»)

В предыдущей итерации были заложены архитектурные решения, обеспечивающие масштабируемость и расширяемость:

- **Многослойная архитектура**:
  
  - API слой: тонкие контроллеры, только приём/валидация запросов.
  - Application слой: реализация бизнес-сценариев и оркестрация обработки.
  - Domain слой: доменные сущности (`File`, `Form`, `FlatData`) и контракты.
  - Infrastructure слой: реализации работы с MongoDB и парсинга Excel.

- **Конфигурационная сущность `Form`**:
  
  - хранит идентификатор, название, ключевые слова (например, для разделов «Справочно»), список пропускаемых листов.
  - задаёт правила обработки и служит основой для выбора обработчика.

- **Обработка через FormHandler и единый конвейер**:
  
  - `UploadService` получал `Form` по `form_id`.
  - определялся подходящий `FormHandler`.
  - запускался единый конвейер обработки (валидация, метаданные, обработка листов, формирование `FlatData`, округление, заметки).

- **Поддержка 5-ФК** как «универсального и наименее формализованного» формата:
  
  - были описаны отдельные компоненты: обработчик формы, валидатор, извлечение метаданных, универсальный парсер листов, локатор таблиц, стратегии округления.
  - акцент делался на эвристических алгоритмах обнаружения структуры таблиц.

## 3. Текущее состояние системы

### 3.1. API и сценарии работы

На текущий момент приложение реализовано на FastAPI и использует версионирование `v2`. Основные группы эндпоинтов включают:

- `upload` — приём файлов и запуск обработки;
- `upload_progress` — выдача прогресса обработки в реальном времени;
- `files` — получение сведений о загруженных файлах;
- `filters` — выборка данных и работа с фильтрами;
- `forms` — управление сущностями форм;
- `logs` — получение логов для наблюдаемости и диагностики;
- `health` — проверка состояния сервиса.

Дополнительно реализованы централизованные обработчики исключений на уровне приложения: ошибки запросов и необработанные исключения логируются, что улучшает поддержку и диагностику в эксплуатации.

### 3.2. Архитектурный срез: появление фиксированных пайплайнов Upload и Parsing

Ключевое изменение текущей итерации — формализация обработки в виде **двух фиксированных пайплайнов**:

- `app/application/upload` отвечает за жизненный цикл файла как сущности (валидация, регистрация, чтение, разбор листов, сохранение/rollback);
- `app/application/parsing` отвечает за парсинг **одного листа** через последовательность шагов и накопление результата в доменной модели листа.

Это убрало «размазанную» по сервисам обработку и превратило её в управляемую, наблюдаемую цепочку операций с единым контрактом ошибок.

### 3.4. Двухфазная загрузка (Upload) и прогресс выполнения

Пользовательский сценарий загрузки перестроен на **двухфазную модель**:

1. `POST /api/v2/upload`:
   
   - принимает файлы и `form_id`;
   - возвращает `202 Accepted` и `upload_id`;
   - запускает фоновую обработку (асинхронная задача).

2. `GET /api/v2/upload-progress/{upload_id}`:
   
   - отдаёт SSE-поток прогресса (статус, количество обработанных файлов, проценты);
   - финальное событие содержит полный итоговый `UploadResponse` (результат по каждому файлу);
   - после завершения запись прогресса очищается из памяти.

Технически это реализовано через `UploadManager` + хранилище `UploadProgress` в памяти процесса.

### 3.5. Upload Pipeline: фиксированная последовательность шагов и единая модель ошибок

#### 3.5.1. Сборка пайплайна

Фиксированный набор шагов собирается в `app/application/upload/pipeline/pipeline.py`:

```python
steps = [
    AcquireFileRecordStep(file_service),
    ReadFileContentStep(),
    ExtractMetadataStep(file_service),
    ReadWorkbookStep(),
    ProcessSheetsStep(parsing_registry=parsing_registry),
    FinalizeFileModelStep(),
    EnrichFlatDataStep(),
    PersistStep(data_save_service),
]
```

Таким образом, архитектурно закреплено:

- где именно создаётся запись файла;
- в какой момент появляется «снимок» содержимого;
- где выполняется парсинг листов;
- в какой точке результаты превращаются в `flat_data` и сохраняются.

#### 3.5.2. Обработка ошибок и rollback

`UploadPipelineRunner` реализует единый контракт ошибок:

- `CriticalUploadError` / `CriticalParsingError`:
  
  - логируются;
  - помечают файл как failed;
  - инициируют `data_save_service.rollback(...)` (если запись файла уже создана);
  - останавливают обработку текущего файла.

- `NonCriticalUploadError` / `NonCriticalParsingError`:
  
  - логируются;
  - добавляются в `warnings` контекста;
  - выполнение пайплайна продолжается.

- `DuplicateFileError`:
  
  - отдельный «сигнальный» сценарий (повторная загрузка / нарушение уникальности), который не требует трактовать ситуацию как «падение сервера».

Ключевое следствие: стратегия «что является критичным» зафиксирована на уровне типов исключений, а не размазана по обработчикам.

### 3.6. Связывание Upload → Parsing: единая точка входа через ProcessSheetsStep

Шаг `ProcessSheetsStep` — граница между пайплайнами:

- получает листы из прочитанной рабочей книги (`ctx.workbook_sheets`);
- для каждого листа запрашивает pipeline парсинга через `ParsingStrategyRegistry.build_pipeline_for_sheet(...)`;
- создаёт `ParsingPipelineContext`, запускает `ParsingPipelineRunner`;
- при критической ошибке парсинга поднимает `CriticalUploadError`, тем самым переводя ошибку листа в ошибку файла.

Это важное архитектурное решение: **Upload Pipeline** остаётся владельцем судьбы файла, а **Parsing Pipeline** отвечает только за корректность парсинга листа.

### 3.7. Parsing Pipeline: контекст, шаги и «источник правды» результатов

#### 3.7.1. Контекст и инварианты

`ParsingPipelineContext` фиксирует единый формат обмена данными между шагами. При этом итоговые результаты пишутся в доменную модель листа — `SheetModel`.

В контексте зафиксирована ключевая идея: **`sheet_model` — единственный источник правды** по результатам парсинга (заголовки, `flat_data_records`, `warnings`, `errors`). Контекст хранит лишь промежуточные значения (`processed_dataframe`, `table_structure`, `extracted_data`).

#### 3.7.2. Оркестратор шагов и политика обработки ошибок

`ParsingPipelineRunner` исполняет шаги для одного листа и применяет единый контракт ошибок:

- `CriticalParsingError`:
  
  - логируется;
  - записывается в `ctx.errors`;
  - пробрасывается наверх (пайплайн не «глотает» критические ошибки).

- `NonCriticalParsingError`:
  
  - логируется;
  - превращается в warning;
  - выполнение продолжается.

Это позволяет расширять набор шагов, не нарушая единых правил поведения пайплайна при ошибках.

#### 3.7.3. Фиксированный набор шагов parsing pipeline (канонический порядок)

В отличие от предыдущей итерации, где «конвейер» описывался в основном концептуально, текущая реализация закрепляет **канонический порядок шагов** на уровне базовой стратегии `DefaultFormParsingStrategy`.

Сборка pipeline выполняется в `app/application/parsing/strategies/base.py` в методе `build_steps_for_sheet(...)`. Шаги формируются строго в следующем порядке:

1. `NormalizeSheetNameStep(normalize_fn=...)`
   
   - нормализует имя листа (опционально, через функцию стратегии);
   - результат фиксируется в `sheet_model.sheet_name` и используется в логах/ключах.

2. `NormalizeDataFrameStep()`
   
   - ищет строку нумерации столбцов `1..n`;
   - обрезает DataFrame по найденным границам;
   - при отсутствии нумерации поднимает `CriticalParsingError`.

3. `DetectTableStructureStep()`
   
   - определяет структуру таблицы (`TableStructure`) и сохраняет её в `ctx.table_structure`;
   - подготавливает основу для корректного выделения заголовков и данных.

4. **Форма-специфичные шаги (hook стратегии)**
   
   - добавляются между структурой и парсингом заголовков;
   - возвращаются стратегией через `get_additional_steps_before_headers(...)`.
   
   Пример для 1ФК:
   
   - `FK1RoundingStep()` (условно, для выбранных листов);
   - `ProcessNotesStep()` (выполняется всегда).

5. `ParseHeadersStep(...)`
   
   - выделяет иерархические горизонтальные и вертикальные заголовки;
   - поддерживает настройку «обрезки» ведущих уровней горизонтальных заголовков
     (например, убрать префиксы уровня «Раздел» или «ОКЕИ») через параметры стратегии.

6. `ExtractDataStep(deduplicate_columns=...)`
   
   - извлекает блок данных по найденной структуре/заголовкам;
   - опционально дедуплицирует колонки (флаг управляется стратегией и/или requisites формы).

7. `GenerateFlatDataStep()`
   
   - строит плоские записи `flat_data_records` и записывает их в `sheet_model`.

Важно, что шаги выполняются **строго последовательно** и опираются на единый контекст, что делает парсинг воспроизводимым и упрощает локализацию ошибок.

#### 3.7.3. Пример шага: нормализация DataFrame

Например, `NormalizeDataFrameStep` выполняет предобработку: ищет строку нумерации столбцов 1..n, обрезает DataFrame до «валидных» границ. Если строка не найдена — выбрасывает `CriticalParsingError`, так как дальнейший парсинг станет недостоверным.

### 3.8. Разделение стратегий парсинга: реестр и точки расширения

Вместо «выбора FormHandler» текущая система использует `ParsingStrategyRegistry` — это единая точка принятия решений:

- выбирает стратегию по `form_info.type`;
- применяет **manual-стратегии** для форм с ручной логикой (например, `FK_1`);
- для остальных форм использует **стратегию по умолчанию** `AutoFormParsingStrategy`.

Технически это реализовано так:

- при создании реестра инициализируется `_default = AutoFormParsingStrategy()`;
- ручные формы регистрируются явно в `_register_manual_forms()`;
- метод `get_strategy(form_type)` возвращает конкретную стратегию или `_default`.

#### 3.8.1. Как решается, обрабатывать ли лист

Перед тем как строить шаги, стратегия проверяет лист через `should_process_sheet(sheet_name, sheet_index, form_info)`:

- для автоформ (`AutoFormParsingStrategy`):
  
  - обрабатываются только листы с именем вида `РазделN` (любой регистр, пробелы допускаются);
  - учитывается `skip_sheets` в `form_info.requisites` (пропуск по индексу листа).

- для 1ФК (`FK1FormParsingStrategy`):
  
  - имя сначала нормализуется к каноническому виду `РазделN`;
  - обрабатываются только листы из заранее заданного набора (`Раздел0..Раздел7`);
  - также учитывается `skip_sheets`.

Если `should_process_sheet` вернул `False`, `ProcessSheetsStep` не считает это ошибкой — лист просто пропускается.

#### 3.8.2. Какие параметры стратегии реально влияют на pipeline

Помимо самого факта обработки листа, стратегия задаёт вариативность через контролируемые «хуки» `DefaultFormParsingStrategy`:

- `get_normalize_sheet_name_fn(...)`:
  
  - возвращает функцию нормализации имени листа или `None`.

- `get_additional_steps_before_headers(...)`:
  
  - добавляет форма-специфичные шаги между `DetectTableStructureStep` и `ParseHeadersStep`.

- `get_deduplicate_columns(...)`:
  
  - управляет поведением `ExtractDataStep(deduplicate_columns=...)`.

- `get_horizontal_header_leading_levels_to_drop(...)` и `get_horizontal_header_strip_fk1_banner(...)`:
  
  - настраивают “очистку” горизонтальных заголовков, чтобы результирующие ключи/пути были стабильно сопоставимы.

Точка расширения для новой формы теперь выглядит так:

1. создать стратегию в `app/application/parsing/strategies/*`;
2. зарегистрировать её в `ParsingStrategyRegistry._register_manual_forms()`;
3. описать шаги парсинга листа через `build_steps_for_sheet(...)`.

За счёт этого добавление новых форм чаще всего сводится к добавлению стратегии и набора шагов, не изменяя «скелет» пайплайнов.

### 3.9. Инициализация системы и сопровождение форм

При старте приложения выполняются операции, усиливающие устойчивость и управляемость:

- создание индексов в базе данных;
- инициализация реестра стратегий парсинга;
- обеспечение наличия системных форм (автоматическое создание при отсутствии).

Это снижает вероятность ошибок окружения и упрощает развёртывание.

## 4. Основные отличия текущей итерации от предыдущей («новой архитектуры»)

### 4.1. Эволюция конвейера обработки

Было (предыдущая итерация):

- основной сценарий описывался через `UploadService` + `FormHandler`;
- «единый конвейер» являлся концепцией (валидация → метаданные → листы → flat data → сохранение).

Стало (текущая итерация):

- конвейер реализован как **явный пайплайн** со стандартными шагами и единым контекстом;
- добавлена формальная классификация ошибок (critical / non-critical / duplicate);
- добавлен rollback на критических ошибках и сохранение частичного результата в прогресс задачи.

### 4.2. Изменение пользовательского сценария загрузки

Было:

- `POST /upload` возвращал итоговый ответ после завершения обработки.

Стало:

- `POST /upload` стал неблокирующим (202 + `upload_id`);
- прогресс и итоговый результат выдаются через отдельный SSE-эндпоинт.

### 4.3. Развитие механизма расширяемости форм

Было:

- расширение происходило через добавление новых обработчиков форм и настройку `Form`.

Стало:

- расширение выполняется через регистрацию стратегий в `ParsingStrategyRegistry` и добавление шагов парсинга;
- появилась чёткая точка входа «построить пайплайн для листа» (можно пропускать листы на уровне стратегии);
- усилилась поддержка режима «авто» (стратегия по умолчанию для большинства форм).

### 4.4. Наблюдаемость, диагностика и эксплуатационные свойства

В текущей версии усилился фокус на эксплуатационных качествах:

- добавлен API для логов;
- реализовано логирование ошибок в обработчиках исключений приложения;
- улучшено сопровождение прогресса загрузки;
- частично внедрена метрика `files_processed`.

## 6. Заключение

Текущая итерация проекта развивает заложенную ранее «новую архитектуру» в сторону эксплуатационной готовности и устойчивости:

- обработка файлов реализована как формальный пайплайн шагов с чётким управлением ошибками и rollback;
- пользовательский сценарий загрузки модернизирован до двухфазной схемы (202 + SSE-прогресс);
- расширяемость парсинга обеспечена через реестр стратегий и композицию шагов;
- существенно усилены контроль целостности данных, тестирование и наблюдаемость.

В результате система стала более предсказуемой в поведении, проще в сопровождении и лучше адаптирована к вариативным входным данным и росту функциональности.
