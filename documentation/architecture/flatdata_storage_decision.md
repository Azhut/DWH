# Решение по хранению `FlatData`

## Контекст

В проекте основная таблица данных хранится в коллекции MongoDB `FlatData`.
Каждая запись представляет одну ячейку нормализованной таблицы:

```json
{
  "year": 2025,
  "reporter": "5-ФК АРТИНСКАЯ СШ — КОПИЯ — КОПИЯ",
  "section": "Раздел1",
  "row": "Организации в ведении органов управления в сфере физической культуры и спорта",
  "column": "№ строки",
  "value": 1,
  "file_id": "8c5f4272-1173-4e5d-9e48-ecf3fa12e1de",
  "form": "eab639f7-78c4-4e08-bd27-756bac5cf571"
}
```

За 3 года накоплено около 27 млн записей. Ожидаемый ежегодный прирост — около 7 млн записей.
Объём данных в MongoDB — около 9 ГБ.

Остальные коллекции (`Files`, `Forms`, `Logs`) существенно меньше и выполняют роль метаданных, состояния загрузок и журналов.

## Основная проблема

MongoDB используется как хранилище для большой аналитической таблицы.
Это работает для точечных выборок с несколькими фильтрами, но плохо подходит для частого получения уникальных значений полей (`distinct`) по большой коллекции.

Наиболее проблемный сценарий:

1. Пользователь выбирает форму (`form_id`).
2. Открывает интерфейс фильтров.
3. Запрашивает список уникальных значений для одного поля: `year`, `reporter`, `section`, `row` или `column`.
4. После выбора значения следующий список фильтра строится уже с учётом выбранных условий.

Например:

```text
Получить все уникальные row
для form = X
и year = 2026
```

Такие запросы могут быть медленными, потому что MongoDB вынуждена сканировать значительную часть индекса или коллекции.

## Пользовательский сценарий

Основной сценарий работы пользователя:

1. Пользователь открывает веб-интерфейс.
2. Видит предпросмотр 10 строк таблицы с колонками:
   - `year`
   - `reporter`
   - `section`
   - `row`
   - `column`
   - `value`
3. Открывает панель фильтров.
4. Последовательно выбирает значения фильтров.
5. Получает отфильтрованную таблицу.
6. Экспортирует результат в CSV или Excel.

Одновременных пользователей мало: обычно 1, редко до 3.

## Требования

### Функциональные

- Хранить нормализованные данные `FlatData`.
- Получать уникальные значения фильтров с учётом уже выбранных фильтров.
- Получать отфильтрованные строки таблицы.
- Экспортировать результат в CSV/Excel.
- Удалять данные по `file_id`.
- Удалять данные по `form`.
- Поддерживать работу только в рамках выбранной формы (`form_id` всегда присутствует в запросах).

### Нефункциональные

- Минимально переписывать существующую архитектуру.
- Сохранить MongoDB для метаданных.
- Ускорить запросы `distinct` и фильтрацию по большой таблице.
- Обеспечить контролируемую загрузку больших объёмов данных.
- Явно контролировать дедупликацию.
- Иметь понятный rollback/cleanup при ошибках загрузки.
- Не усложнять инфраструктуру без необходимости.

## Рассмотренные варианты

### MongoDB-only

Оставить все данные в MongoDB и оптимизировать текущую схему.

Возможные улучшения:

- добавить дополнительные индексы под частые комбинации фильтров;
- создать отдельную коллекцию предрасчитанных значений фильтров;
- кэшировать `distinct`-запросы;
- пересчитывать фильтры после загрузки формы или файла.

Плюсы:

- минимальная миграция;
- текущая архитектура уже использует MongoDB;
- есть уникальные индексы;
- проще сохранять текущую модель удаления и rollback.

Минусы:

- MongoDB остаётся неидеальным инструментом для аналитических `distinct`/`group by`;
- индексы могут сильно разрастаться;
- проблема производительности может вернуться при росте данных;
- предрасчитанные фильтры усложняют логику консистентности.

### PostgreSQL

Перенести `FlatData` или всю систему в PostgreSQL.

Плюсы:

- строгие транзакции;
- `UNIQUE` constraints;
- понятный rollback;
- хорошая поддержка SQL;
- предсказуемое удаление и обновление данных;
- можно хранить всю систему в одной БД.

Минусы:

- миграция крупнее;
- придётся переписывать больше репозиториев;
- одна большая таблица на десятки миллионов строк всё равно потребует аккуратных индексов;
- аналитические запросы будут быстрее MongoDB, но обычно медленнее DuckDB/ClickHouse.

### DuckDB + MongoDB

Оставить MongoDB для метаданных, а `FlatData` перенести в DuckDB.

Плюсы:

- хорошо подходит для большой плоской аналитической таблицы;
- быстрые `distinct`, фильтрация, агрегации и экспорт;
- не нужен отдельный сервер БД;
- можно заменить только `FlatDataRepository`, почти не меняя API;
- остальные коллекции остаются в MongoDB;
- дешёвое и простое инфраструктурное решение.

Минусы:

- DuckDB — embedded-хранилище, а не серверная OLTP-БД;
- запись должна быть организована как одиночный контролируемый процесс;
- конкурентные записи нежелательны;
- уникальность и rollback нужно явно проектировать на уровне протокола загрузки;
- при росте до нескольких API-инстансов архитектуру придётся пересматривать.

## Предложенное решение

Рекомендуемый вариант: **гибридная архитектура MongoDB + DuckDB**.

MongoDB остаётся для:

- `Files`;
- `Forms`;
- `Logs`;
- статусов загрузки;
- метаданных форм и файлов.

DuckDB используется только для:

- `FlatData`;
- фильтрации;
- получения уникальных значений фильтров;
- подготовки данных для экспорта.

Такой вариант минимально затрагивает существующую архитектуру, потому что `FlatData` уже выделен в отдельный доменный агрегат и репозиторий.

## Предлагаемая схема DuckDB

```sql
CREATE TABLE flat_data (
    form TEXT NOT NULL,
    file_id TEXT NOT NULL,
    year INTEGER NOT NULL,
    reporter TEXT NOT NULL,
    section TEXT NOT NULL,
    row TEXT NOT NULL,
    column TEXT NOT NULL,
    value DOUBLE
);
```

Основной бизнес-ключ:

```text
file_id + year + reporter + section + row + column
```

Для загрузки используется staging-таблица:

```sql
CREATE TABLE flat_data_staging (
    upload_id TEXT NOT NULL,
    form TEXT NOT NULL,
    file_id TEXT NOT NULL,
    year INTEGER NOT NULL,
    reporter TEXT NOT NULL,
    section TEXT NOT NULL,
    row TEXT NOT NULL,
    column TEXT NOT NULL,
    value DOUBLE
);
```

## Протокол загрузки

Загрузка не должна писать данные напрямую в основную таблицу.

Рекомендуемый процесс:

1. Создать запись в MongoDB `Files` со статусом `PROCESSING`.
2. Распарсить Excel-файл.
3. Записать данные в `flat_data_staging` с конкретным `upload_id`.
4. Проверить дубли внутри staging.
5. Проверить пересечение с уже существующими данными в `flat_data`.
6. Если проверки успешны, перенести данные из staging в `flat_data`.
7. Удалить staging-данные по `upload_id`.
8. Обновить статус файла в MongoDB на `SUCCESS`.
9. При ошибке удалить staging-данные и пометить файл как `FAILED`.

Проверка дублей внутри staging:

```sql
SELECT
    file_id,
    year,
    reporter,
    section,
    row,
    column,
    COUNT(*) AS duplicates_count
FROM flat_data_staging
WHERE upload_id = ?
GROUP BY
    file_id,
    year,
    reporter,
    section,
    row,
    column
HAVING COUNT(*) > 1;
```

Проверка пересечения с основной таблицей:

```sql
SELECT COUNT(*)
FROM flat_data AS main
JOIN flat_data_staging AS staging
    ON main.file_id = staging.file_id
   AND main.year = staging.year
   AND main.reporter = staging.reporter
   AND main.section = staging.section
   AND main.row = staging.row
   AND main.column = staging.column
WHERE staging.upload_id = ?;
```

## Rollback и cleanup

Для больших загрузок в текущей MongoDB-архитектуре уже используется компенсирующая очистка по `file_id`, если полная транзакция невозможна.
При переносе `FlatData` в DuckDB этот подход сохраняется, но становится более явным.

Правила:

- если ошибка произошла до переноса в `flat_data`, удалить staging по `upload_id`;
- если ошибка произошла после переноса, удалить данные из `flat_data` по `file_id`;
- статус файла в MongoDB установить в `FAILED`;
- пользовательские запросы должны учитывать только файлы со статусом `SUCCESS` либо полагаться на то, что в `flat_data` попадают только успешно завершённые загрузки.

## Удаление

Удаление файла:

1. Удалить данные из DuckDB по `file_id`.
2. Удалить документ из MongoDB `Files`.
3. Записать событие в `Logs`.

Удаление формы:

1. Удалить данные из DuckDB по `form`.
2. Удалить файлы формы из MongoDB `Files`.
3. Удалить форму из MongoDB `Forms`.
4. Записать событие в `Logs`.

Для повышения надёжности можно добавить повторяемые cleanup-операции:

- `delete_by_file_id(file_id)`;
- `delete_by_form_id(form_id)`;
- `delete_staging_by_upload_id(upload_id)`.

Эти операции должны быть идемпотентными.

## Изменения в коде

Минимальный путь внедрения:

1. Добавить слой подключения к DuckDB.
2. Добавить `DuckDBFlatDataRepository` с тем же контрактом, что у текущего `FlatDataRepository`.
3. Перевести методы:
   - `distinct`;
   - `get_filtered_data`;
   - `bulk_write_ops` / batch insert;
   - `delete_by_file_id`;
   - `delete_by_form`.
4. Обновить dependency wiring, чтобы `FlatDataService` использовал DuckDB-репозиторий.
5. Оставить API-контракт без изменений.
6. Добавить протокол staging-загрузки и проверки дублей.
7. Добавить настройку пути к файлу DuckDB через env/config.

## Миграция данных

Есть два возможных пути.

### Вариант 1. Загрузить данные заново

Предпочтительный вариант, если исходные Excel-файлы доступны.

Плюсы:

- не нужно выгружать 27 млн записей из MongoDB;
- можно сразу проверить корректность парсинга;
- можно один раз построить новую DuckDB-таблицу с чистого состояния.

Минусы:

- пользователям нужно повторно загрузить данные;
- важно сделать процесс достаточно надёжным, чтобы это потребовалось только один раз.

### Вариант 2. Миграция из MongoDB

Выгрузить существующую `FlatData` из MongoDB чанками и загрузить в DuckDB.

Плюсы:

- пользователям не нужно повторно загружать файлы.

Минусы:

- потребуется отдельный миграционный скрипт;
- нужно аккуратно контролировать память;
- нужно валидировать количество строк и дубли;
- миграция может быть долгой.

## Риски

- DuckDB не подходит для частых конкурентных записей.
- При нескольких API-контейнерах запись в один DuckDB-файл может стать проблемой.
- Нужно явно реализовать staging, дедупликацию и cleanup.
- Нужно следить за резервным копированием DuckDB-файла.
- При росте системы может потребоваться переход на PostgreSQL или ClickHouse.

## Итоговая рекомендация

Для текущих условий проекта оптимальным выглядит гибридный вариант:

```text
MongoDB: метаданные, формы, файлы, логи
DuckDB: большая таблица FlatData
```

Это решение:

- минимально переписывает существующую архитектуру;
- решает основную проблему с медленными `distinct`-запросами;
- не требует отдельного серверного хранилища;
- сохраняет MongoDB там, где она уже хорошо работает;
- позволяет явно контролировать загрузку, дедупликацию и rollback через staging-протокол.

Если в будущем появятся частые конкурентные записи, несколько API-инстансов или требования к строгой единой транзакционности между всеми таблицами, стоит пересмотреть решение в сторону PostgreSQL.
